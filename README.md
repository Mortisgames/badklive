# BADK Live

Статичний україномовний дашборд історичних показників балістичної загрози.
Джерело — сім публічних CSV-аркушів Google Sheets; Telegram-стрічка незалежно
завантажується через сторонній читач. Розрахунок основної моделі знаходиться
поза цим репозиторієм. У браузері немає runtime-залежностей або збірки модулів.

## Локальний запуск

Потрібен Node.js 22+.

```sh
npm ci
npm start
```

Відкрити http://127.0.0.1:4173. ES-модулі потребують HTTP-сервера, а не `file://`.
Service worker на localhost вимкнений за замовчуванням; для перевірки PWA
відкрити `/?pwa`. Після PWA-тестування видаліть реєстрацію worker і кеші
цього застосунку в DevTools або використовуйте окремий профіль браузера.

## Структура

- `index.html`, `assets/app.css` — єдина сторінка дашборда та її стилі.
- `badk-live-dashboard.html` — перенаправлення старого URL.
- `js/app.js`, `js/state.js` — запуск, оновлення і заміна знімка.
- `js/data/` — CSV, контракти, парсери, запити, кеш та календарна статистика.
- `js/views/dashboard.js` — відображення розділів і навігація.
- `js/feed.js`, `js/game.js`, `js/pwa.js` — стрічка, мінігра, встановлення worker.
- `scripts/sw-runtime.js` — вихідний код worker; `sw.js` генерується автоматично.

## Дані та відмови

Оновлення кожні 10 хвилин: завантажити всі сім листів → перевірити → побудувати
новий знімок → замінити стан → зберегти CSV для офлайн-відновлення.
Невдалий запит або перевірка не змінює попередні дані. Один запит обмежений
20 секундами, включно з читанням тіла відповіді. Повторні оновлення використовують
ту саму операцію; при помилці решта запитів скасовується. Атомарність стосується
стану клієнта: Google Sheets не гарантує транзакційність між окремими експортами.

Контракти у `js/data/validation.js` перевірені за заголовками джерела.
Порожній HTTP-вміст — помилка; лист із заголовками без записів — допустимий.
Аркуші «Оперативна оцінка» та «Контроль» мають секційну структуру й перевіряються
за обов'язковими маркерами; їхні текстові пояснення не обмежені числовою схемою.
Порожнє значення атаки зберігається як `null`. Неперевірені дні та дні без
покриття не входять у знаменник статистики. Пропуски дат позначаються невідомими.

Кеш v2 повторно перевіряється при читанні. Сумісний старий кеш v1 мігрує
автоматично, зберігаючи початковий час отримання. Старі знімки не видаляються
за віком: інтерфейс показує дату отримання та цільову дату даних.

## Офлайн-оболонка й оновлення

HTML, CSS, модулі та зображення попередньо кешуються одним комплектом.
Оболонка використовує cache-first, щоб новий HTML не завантажував модулі
попереднього випуску. На відміну від початкового плану з network-first для HTML,
це забезпечує узгодженість версії після поділу на ES-модулі.
Новий worker очікує кнопки «Доступне оновлення — перезавантажити».
Запити до таблиць, проксі, шрифтів і сторонніх шляхів worker не перехоплює.
Видаляються лише попередні випуски з префіксом поточного scope. Старі спільні
кеші v3 залишаються недоторканими: їх неможливо безпечно прив'язати до scope.

Після змін HTML, стилів, модулів, іконок або runtime worker:

```sh
npm run prepare:sw
npm run check
npm test
npx playwright install chromium
npm run test:browser
```

Версія `sw.js` обчислюється за вмістом усіх офлайн-файлів. `check` перевіряє
синтаксис, локальні імпорти, ресурси manifest та актуальність списку кешування.
Тести використовують невеликі штучні CSV з `tests/fixtures/`, без звернення
до живої таблиці. Браузерні тести перевіряють вкладки, мобільний екран, відмови,
офлайн-відновлення, старий URL і прийняття оновлення.

GitHub Actions запускає перевірки для PR і main. Публікація main дозволена лише
після їх успіху. `scripts/stage.mjs` пакує в `_site/` лише файли застосунку;
тести, node_modules та допоміжні скрипти не потрапляють у Pages.
